# Contributing to Agentic Clinic

Welcome to the **Agentic Clinic** engineering team! We are a university graduation project team composed of five software engineering students. Each of us pairs with an AI coding agent on our local development machines. 

To maintain velocity, safety, and code quality across parallel streams, all contributors (human and AI) must adhere to these guidelines.

---

## 1. Core Principles

1. **Safety & Zero Database Direct Access:** The LLM must NEVER query or write to the database directly. All mutations occur via the Clinic Backend API.
2. **Contract-Driven Development:** Never implement an API or an AI tool without verifying or first updating its contract in `docs/architecture/`.
3. **AI Code is Untrusted by Default:** All AI-suggested code must be verified, tested, and reviewed by a human team member before merging.
4. **Synthetic Data Only:** Never use or commit real patient data. Use only synthetic fixtures adhering to the schemas in `docs/architecture/database-schema.md`.
5. **Zero Secrets in Git:** Never commit API keys, tokens, or credentials. Use local `.env` files.

---

## 2. Git & Branching Workflow

### Protected Branch
- `main` is our production/release-ready stable branch. **Direct commits to `main` are strictly prohibited.**

### Branch Types
Branches represent **units of work**, never individual team members. Name your branch according to the intent of the change:

| Prefix | Purpose | Example |
| :--- | :--- | :--- |
| `feature/` | New functionality or tool integration | `feature/doctor-availability-api` |
| `fix/` | Bug fixes or issue resolutions | `fix/double-booking-prevention` |
| `refactor/`| Code improvements without behavior changes | `refactor/audio-buffer-pool` |
| `test/` | Adding or updating tests | `test/cancellation-tool-schemas` |
| `docs/` | Architecture, contracts, or guide updates | `docs/egyptian-arabic-eval-plan` |
| `experiment/`| Non-production prototypes and benchmarks | `experiment/stt-whisper-latency` |

### Starting Work
```bash
# Ensure your local main is up to date
git checkout main
git pull origin main

# Create your feature branch
git checkout -b feature/<descriptive-name>
```

## 3. Commit Convention (Conventional Commits)

All commits must follow the **Conventional Commits** specification:

```
<type>: <short imperative summary>

[optional body explaining why and what]

[optional references, e.g., Closes #12]
```

### Allowed Types:
- `feat`: A new feature (e.g. `feat: add doctor availability endpoint`)
- `fix`: A bug fix (e.g. `fix: prevent duplicate appointment booking`)
- `refactor`: Code change that neither fixes a bug nor adds a feature
- `test`: Adding missing tests or correcting existing tests
- `docs`: Documentation only changes
- `chore`: Changes to build process, tooling, or repository hygiene
- `perf`: A code change that improves performance or latency
- `security`: Security patches, auth enforcement, or secret prevention

## 4. Pull Requests (PRs) & Code Review

### Creating a PR
- Push your branch to the remote repository.
- Open a PR against `main`.
- Fill out the **Pull Request Template** completely (`.github/PULL_REQUEST_TEMPLATE.md`).
- Ensure CI checks pass.

### Code Review Rules
- **No Self-Merges:** The author of a branch may not merge their own PR.
- **Reviewer Rotation:** Each PR must be reviewed and approved by at least one other team member. Reviews should rotate across the 5 members to disseminate domain knowledge.
- **Reviewing AI-Generated Code:** When reviewing code generated by an AI assistant:
  1. Inspect for hallucinations, unexpected imports, or unnecessary libraries.
  2. Verify edge-case handling (e.g., date formats, timezone offsets, missing parameters).
  3. Ensure that contracts in `docs/architecture/` were strictly respected.
  4. Verify that comprehensive automated tests accompany the PR.

---

## 5. Testing & Verification

Tests are a required deliverable for any pull request:
- **Unit Tests:** Fast, in-memory validation of services and tools.
- **Integration Tests:** Verify communication across service contracts.
- **E2E & Evaluation Tests:** Conversational trajectory tests and Arabic dialect benchmarks.

Run tests before pushing:
```bash
# Validate repository structure & contracts
python scripts/validate_repo.py
```

---

## 6. Documentation & Architecture Decision Records (ADRs)

- If you modify an API endpoint or tool schema, update `docs/architecture/api-contracts.md` or `docs/architecture/tool-schemas.md` in the same PR.
- If you introduce a significant architectural change (e.g., changing vector database, adopting a new voice protocol, or introducing a library), you must author an Architectural Decision Record in `docs/decisions/` using the format in [docs/decisions/README.md](docs/decisions/README.md).
