## 1. Callers & Authentication

**Implementation status (2026-10-14):** catalog, conversations and identity are implemented; shared Oracle registration/email verification through n8n is tested. Doctor availability and earliest-slot search (§5.4–5.5) are implemented and deployed to Oracle with migration 0004 after user approval. Appointment writes, tickets and idempotency remain planned. Public limits remain single-process; identity limits are atomic in PostgreSQL. See [availability review notes](../development/phase1-availability-changes.md). These markers do not change ADR acceptance.

### 1.1. Who calls the backend

| Caller | What it is | Credentials it holds |
|---|---|---|
| **Call page** | The browser web page (call button, code box, registration form) | Conversation token only |
| **Agent service** | `services/ai-agent` (and `services/voice` for call lifecycle events) | Service token + the conversation token of the current call |
| **Clinic staff** | Dashboard users | Staff credentials — **defined in a later PR** (§8) |

The **LLM is not a caller**. It never sees any token, any internal patient id, or any verification code. Tools in `services/ai-agent` call this API and attach credentials outside the model context.

### 1.2. Headers

| Header | Value | Sent by |
|---|---|---|
| `X-Conversation-Token` | Opaque token from `POST /conversations` (≥ 32 random bytes, base64url) | Call page, agent service |
| `X-Service-Token` | `AGENT_SERVICE_TOKEN` from configuration | Agent / voice service only. Never sent to or stored in the browser |
| `Idempotency-Key` | 8–128 chars, `[A-Za-z0-9_-]` | Agent service, on the four write operations (§1.5) |
| `X-Request-Id` | Optional client id; generated by the backend if absent | Anyone. Echoed in every response and error |

### 1.3. Access levels

| Level | Requirements | Used for |
|---|---|---|
| **Public** | None (rate-limited per IP) | Catalog: specialties, doctors, availability, services |
| **Conversation** | Valid `X-Conversation-Token` (conversation `active` or within the resume window) | Call page: verification code entry, registration |
| **Service + conversation** | Valid `X-Service-Token` **and** valid `X-Conversation-Token` | Agent: start verification, call lifecycle, escalation |
| **Patient** | Service + conversation **and** a valid patient session bound to that conversation | Agent: everything under `/patients/me/...` |

**Two independent checks (ADR-003 §3.1).** The service token proves the request comes from our agent service and grants no patient permission by itself. The patient is derived **only** from the patient session bound to the conversation. No request field can select or override the patient.

Patient-scoped endpoints are **not** callable from the browser (no service token there). The browser can only submit codes and registration data.

### 1.4. Formats & conventions

| Item | Format |
|---|---|
| Dates | `YYYY-MM-DD`, clinic-local (`Africa/Cairo`) |
| Times of day | `HH:MM` 24-hour, clinic-local |
| Timestamps | ISO-8601 UTC, e.g. `2026-10-10T14:32:00Z` |
| Weekdays | Lowercase English names: `saturday`, `sunday`, `monday`, `tuesday`, `wednesday`, `thursday` |
| Money | `{ "amount": 350.00, "currency": "EGP" }` |
| Bilingual text | Both languages returned: `name_en`, `name_ar` (the agent chooses) |
| Pagination | `limit` (default 20, max 100), `offset` (default 0); responses include `total` |
| Unknown JSON fields in requests | Rejected with `400 VALIDATION_FAILED` |

### 1.5. Idempotency

Required on: book, reschedule, cancel, create ticket. Missing header → `400 IDEMPOTENCY_KEY_REQUIRED`.

- Keys are scoped to **(patient account, operation)**.
- The agent generates one key **per confirmed action** (when the caller says "yes, book it") and reuses it for every retry of that action.

| Situation | Response |
|---|---|
| New key | Operation runs; response stored for 24 h |
| Same key, same request fingerprint, finished | Stored response returned again (same status code and body) |
| Same key, same request fingerprint, still running | `409 IDEMPOTENCY_IN_PROGRESS` |
| Same key, different request fingerprint | `422 IDEMPOTENCY_KEY_REUSED` |

### 1.6. Rate limiting

Exceeded limits return `429 RATE_LIMITED` with a `Retry-After` header (seconds). Values are configuration (ADR-003 §3.2, §3.4):

| Bucket | Default |
|---|---|
| Public endpoints, per IP | 60 requests / minute |
| `POST /conversations`, per IP | 10 / hour |
| Verification codes, per customer number | 3 / 15 min, 60 s between sends |
| Verification codes, per IP | 10 / hour |
| Verification codes, per conversation | 5 total |
| Failed code entries, per IP | 20 / hour |
| Registrations, per IP | 3 / rolling 24 h |

The client IP is read from `X-Forwarded-For` **only** when the request arrives from an address in `TRUSTED_PROXIES`; otherwise the socket address is used. Parse the chain from the trusted edge, never trust arbitrary leftmost values. At conversation creation, record the resolved browser IP. Agent-triggered OTP requests use that stored conversation IP, not the agent server IP; browser registrations and code entries use the currently resolved browser IP. Public ingress strips caller-supplied forwarding headers before adding its own.

Check and append each rate-limit bucket atomically while holding transaction-scoped locks on `(bucket, subject)` in sorted order. Count known and unknown numbers equally, including the 60-second cooldown. Count every registration attempt (including duplicates), and apply send limits per normalized email for registration (3/15 min and 60-second cooldown) as well as per IP/conversation. Multi-worker requests must not bypass limits through count-then-insert races.

### 1.7. Logging rules

- Request bodies of `/verification/verify` and `/registrations` are **never logged**.
- Tokens (`X-Conversation-Token`, `X-Service-Token`) are never logged; logs use the internal conversation id.
- Error responses never echo submitted codes or tokens.

## 2. Error Envelope & Catalog

### 2.1. Envelope

```json
{
  "error": {
    "code": "SLOT_UNAVAILABLE",
    "message": "The requested slot is no longer available.",
    "details": { "doctor_id": 12, "date": "2026-10-15", "start_time": "14:00" },
    "request_id": "req_8f2c1a",
    "timestamp": "2026-10-10T14:32:00Z"
  }
}
```

`message` is English developer text. The agent turns `code` (+ `details`) into a sentence in the caller's language; it never reads `message` aloud.

### 2.2. Catalog

| HTTP | Code | Meaning | Agent guidance |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | Malformed body, wrong types, unknown fields. `details.fields` lists problems | Internal bug; apologise, retry once, then escalate |
| 400 | `IDEMPOTENCY_KEY_REQUIRED` | Write without `Idempotency-Key` | Internal bug |
| 401 | `SERVICE_AUTH_REQUIRED` | Missing / invalid service token | Internal bug; escalate |
| 401 | `CONVERSATION_INVALID` | Missing, unknown or ended conversation | Call must restart |
| 401 | `VERIFICATION_REQUIRED` | No patient session in this conversation | Start verification |
| 401 | `SESSION_EXPIRED` | Patient session expired or revoked | Explain and start verification again |
| 403 | `ACTION_NOT_ALLOWED` | Allowed caller, forbidden action (e.g. agent setting ticket priority `urgent`) | Internal bug |
| 404 | `DOCTOR_NOT_FOUND` | Unknown or inactive doctor | Offer a doctor search |
| 404 | `SERVICE_NOT_FOUND` | Unknown service | Offer the service list |
| 404 | `APPOINTMENT_NOT_FOUND` | Unknown **or not owned by this patient** (never 403, to avoid revealing existence) | List the caller's appointments |
| 404 | `TICKET_NOT_FOUND` | Unknown or not owned | List the caller's tickets |
| 409 | `SLOT_UNAVAILABLE` | Slot taken (incl. concurrent booking) | Offer other slots |
| 409 | `DAILY_LIMIT_REACHED` | Already 2 active appointments that day | Offer another day |
| 409 | `DUPLICATE_DOCTOR_SAME_DAY` | Already booked with this doctor that day | Offer another day or doctor |
| 409 | `ACTIVE_LIMIT_REACHED` | Already 5 active appointments | Explain the limit |
| 409 | `APPOINTMENT_NOT_ACTIVE` | Appointment is cancelled, completed, no-show, or already started | Explain status |
| 409 | `NO_PENDING_CHALLENGE` | Code submitted but no open challenge in this conversation | Request a new code |
| 409 | `IDEMPOTENCY_IN_PROGRESS` | Same key still running | Wait briefly and retry with the same key |
| 410 | `CHALLENGE_EXPIRED` | Code expired, superseded, or too many wrong attempts. `details.reason`: `expired` \| `superseded` \| `too_many_attempts` | Offer a new code |
| 422 | `INVALID_SLOT_TIME` | Not on the :00/:30 grid, outside the shift, or a nonexistent local time | Offer valid slots |
| 422 | `BOOKING_TOO_SOON` | Less than 1 hour from now | Offer later slots |
| 422 | `BOOKING_TOO_FAR_AHEAD` | More than 30 days ahead | Offer dates within 30 days |
| 422 | `CHANGE_WINDOW_CLOSED` | Less than 4 hours before the appointment | Offer transfer to reception |
| 422 | `CLINIC_CLOSED` | Friday or a clinic closure date. `details.reason_en/_ar` for closures | Offer another day |
| 422 | `DOCTOR_UNAVAILABLE` | Not a working day for the doctor, or time off | Offer other days |
| 422 | `SAME_SLOT` | Reschedule to the appointment's current date and time | Ask for a different time |
| 422 | `INVALID_CUSTOMER_NUMBER` | Not 6 digits, or Luhn check digit wrong | Ask the caller to repeat the number |
| 422 | `INVALID_CODE` | Wrong code. `details.attempts_remaining` | Ask to re-type the code |
| 422 | `IDEMPOTENCY_KEY_REUSED` | Same key, different request fingerprint | Internal bug |
| 429 | `RATE_LIMITED` | Limit exceeded; `Retry-After` header | Explain and wait, or escalate |
| 500 | `INTERNAL_ERROR` | Unexpected failure | Apologise; escalate |
| 503 | `SERVICE_UNAVAILABLE` | Database or mail server unavailable | Apologise; escalate |

Validation order for appointment writes (first failure wins): auth → body shape → idempotency → ownership → status → time rules (`INVALID_SLOT_TIME`, `CLINIC_CLOSED`, `DOCTOR_UNAVAILABLE`, `BOOKING_TOO_SOON`, `BOOKING_TOO_FAR_AHEAD`, `CHANGE_WINDOW_CLOSED`) → limits → slot conflict.

## 4. Conversations & Identity

### 4.1. `POST /conversations`

**Implementation status:** conversation/identity endpoints in §4 and minimal
profile §6.1 are implemented locally behind IDENTITY_ENABLED. Email delivery is
tested with Mailpit; real inbox delivery requires SMTP configuration. Patient
bindings are revoked on end/expiry. Gateway transport ownership remains future
work. The service secret stays outside product browser code.

Starts a conversation. Called by the **call page** when the user presses Call (or opens the text chat).

- **Access:** Public (rate-limited per IP)
- **Request:**
  ```json
  { "channel": "voice" }
  ```
  `channel`: `voice` | `text`.
- **Response `201`:**
  ```json
  {
    "conversation_token": "q7Zr…base64url…",
    "channel": "voice",
    "resume_window_seconds": 300
  }
  ```
  The token is returned **only once**. The backend stores only its hash. The page passes it to the voice service when opening the call WebSocket.

---

### 4.2. `POST /conversations/current/events`

Call lifecycle reported by the voice service.

- **Access:** Service + conversation
- **Request:**
  ```json
  { "event": "disconnected" }
  ```
  `event`: `disconnected` (starts the 5-minute resume window) | `reconnected` | `ended`.
- **Rules:**
  - `ended`, or the resume window passing without `reconnected`, ends the conversation and **revokes** its patient session (`revoke_reason` `call_ended` / `resume_expired`).
  - `reconnected` after the window → `401 CONVERSATION_INVALID`.
- **Response `204`.**

---

### 4.3. `GET /conversations/current/verification`

Current verification state of the conversation. Polled by the call page (to show or hide the code box) and read by the agent (to know when to continue).

- **Access:** Conversation (page) or Service + conversation (agent)
- **Response `200`:**
  ```json
  { "state": "pending", "purpose": "login", "expires_at": "2026-10-10T14:37:00Z" }
  ```
  `state`: `none` | `pending` | `verified`. When `verified`:
  ```json
  { "state": "verified", "purpose": "login", "verified_at": "2026-10-10T14:33:10Z" }
  ```
- Never contains codes, emails or patient data.
- When a new challenge is pending, polling shows it ahead of an existing valid
  binding so the page can display code entry. Polling never refreshes idle time.

---

### 4.4. `POST /verification/challenges`

Starts **login** verification for a customer number. Called by the agent (tool `request_verification_code`).

- **Access:** Service + conversation
- **Request:**
  ```json
  { "customer_number": "482133" }
  ```
- **Validation:** exactly 6 digits with a valid Luhn check digit, else `422 INVALID_CUSTOMER_NUMBER`.
- **Behaviour:**
  - Supersedes any pending `login` challenge in this conversation.
  - If the number belongs to an account: generates a 6-digit code, stores its HMAC, emails it.
  - If the number is unknown: creates a challenge that can never succeed and sends nothing.
- **Response `202`** — **identical** for known and unknown numbers:
  ```json
  {
    "state": "pending",
    "purpose": "login",
    "expires_at": "2026-10-10T14:37:00Z",
    "delivery": "email_on_file"
  }
  ```
- **No masked email is returned.** A masked address appears only for real accounts, so returning it would reveal which customer numbers exist. The agent says: "If this number is registered, we've sent a code to the email on file. Please type it in the box on your screen."
- **Errors:** `422 INVALID_CUSTOMER_NUMBER`, `429 RATE_LIMITED`.

---

### 4.5. `POST /verification/verify`

Submits the code typed in the **code box**. This is the **only** way to complete verification; the agent has no endpoint that accepts a code.

- **Access:** Conversation (call page only). Requests carrying `X-Service-Token` are rejected with `403 ACTION_NOT_ALLOWED`. This header rule prevents accidental routing through tools; it is not proof of browser origin. The architecture must keep code entry out of agent/voice routes, SDK callbacks and logs.
- **Request:**
  ```json
  { "purpose": "login", "code": "604913" }
  ```
- **Behaviour:** locks the pending challenge for this conversation and purpose; checks status and expiry; compares the HMAC in constant time.
- **Response `200` (login):**
  ```json
  { "state": "verified", "purpose": "login" }
  ```
  A patient session is created and bound to the conversation. Any previous patient session in the conversation is revoked (`account_switch`).
- **Response `200` (registration):**
  ```json
  { "state": "verified", "purpose": "registration", "customer_number": "482133" }
  ```
  The patient is created, the customer number is shown on the page and emailed, and a patient session is bound. Registration consumes its challenge and creates the patient/session in one transaction. Recheck normalized email uniqueness at completion; serialize concurrent registrations for that email. A registration that lost a uniqueness race fails through the same generic invalid-code flow as an unusable duplicate challenge, never an account-existence error.
- **Errors:** `409 NO_PENDING_CHALLENGE`, `422 INVALID_CODE` (`details.attempts_remaining`), `410 CHALLENGE_EXPIRED`, `429 RATE_LIMITED`.

---

### 4.6. `POST /registrations`

Submits the **registration form** from the call page.

- **Access:** Conversation (call page only); requests carrying `X-Service-Token` return `403 ACTION_NOT_ALLOWED`.
- **Request:**
  ```json
  {
    "full_name": "Ahmed Mansour",
    "phone": "+201012345678",
    "date_of_birth": "1988-04-15",
    "email": "ahmed.mansour@example.com",
    "preferred_language": "ar",
    "privacy_notice_accepted": true
  }
  ```
- **Validation:** E.164 phone; date of birth in the past and age ≤ 120; RFC-valid email ≤ 254 chars; `privacy_notice_accepted` must be `true`.
- **Behaviour:**
  - New email: creates a `registration` challenge holding the form data and emails a code.
  - Email already registered: creates a challenge that can never succeed, and sends the **existing** owner an email: "Someone tried to register with this address. If it was you, use your customer number to sign in."
  - Never links to existing records by name, phone or date of birth.
- **Response `202`** — identical in both cases:
  ```json
  { "state": "pending", "purpose": "registration", "expires_at": "2026-10-10T14:37:00Z" }
  ```
- **Errors:** `400 VALIDATION_FAILED`, `429 RATE_LIMITED`.

---

### 4.7. `POST /patients/me/logout`

Ends the patient session (caller says "log out" or wants to switch account).

- **Access:** Patient
- **Response `204`.** The conversation continues unverified.

### 5.4. `GET /doctors/{doctor_id}/availability`

Free slots for one doctor.

- **Access:** Public
- **Query:** `from_date` (required), `to_date` (optional, default = `from_date`, at most 6 days after `from_date` (7 inclusive dates)).
- **Rules:** returns only slots that satisfy **all** booking rules at the time of the request (shift, working days, closures, time off, lead time ≥ 1 h, horizon ≤ 30 days, not taken). Dates outside the horizon return empty days, not errors.
- **Response `200`:**
  ```json
  {
    "doctor_id": 12,
    "slot_minutes": 30,
    "days": [
      { "date": "2026-10-15", "slots": ["10:00", "10:30", "12:00", "13:30"] },
      { "date": "2026-10-16", "closed": true, "reason": "CLINIC_CLOSED", "slots": [] }
    ]
  }
  ```
  `reason` for empty days: `CLINIC_CLOSED` | `DOCTOR_UNAVAILABLE` | `FULLY_BOOKED` | `OUTSIDE_BOOKING_WINDOW`.
- **Note:** availability is a snapshot, not a reservation. A slot can be taken before booking, which then returns `409 SLOT_UNAVAILABLE`.
- **Errors:** `400 VALIDATION_FAILED` (range > 7 days, bad dates), `404 DOCTOR_NOT_FOUND`.

---

### 5.5. `GET /availability/search`

"First available" search across doctors, e.g. "the earliest cardiologist tomorrow afternoon".

- **Access:** Public
- **Query:**
  - `specialty_id` and `doctor_id` (optional; when both are supplied, filters intersect)
  - `from_date` (required), `to_date` (optional, at most 6 days after `from_date` (7 inclusive dates))
  - `earliest_time`, `latest_time` (optional `HH:MM`, filter on slot start)
  - `limit` (default 5, max 20)
- **Response `200`:** earliest slots first.
- **Validation:** dates strictly `YYYY-MM-DD`; times strictly `HH:MM`. Reject unknown or duplicate query keys. Earliest time is inclusive; latest exclusive. Sort ties by doctor ID and apply the limit after filters. Unmatched search filters return an empty result list.
  ```json
  {
    "results": [
      {
        "doctor": { "id": 12, "name_en": "Dr. Sarah Farouk", "name_ar": "د. سارة فاروق" },
        "date": "2026-10-15",
        "start_time": "14:00"
      }
    ]
  }
  ```

## 6. Patient-Scoped Endpoints

All require **Patient** access (§1.3). The patient is always the one bound to the conversation. Each successful request refreshes the session's idle timer.

### 6.1. `GET /patients/me`

- **Response `200`:**
  ```json
  {
    "customer_number": "482133",
    "first_name": "Ahmed",
    "preferred_language": "ar"
  }
  ```
  No email, phone, date of birth, gender or insurance data is returned to the agent.

---

### 6.2. `GET /patients/me/appointments`

- **Query:**
  - `status`: `scheduled` (default) | `completed` | `cancelled` | `no_show` | `all`
  - `upcoming_only`: `true` (default for `scheduled`) | `false`
  - `limit`, `offset`
- **Response `200`:**
  ```json
  {
    "total": 1,
    "appointments": [
      {
        "id": 501,
        "doctor": {
          "id": 12,
          "name_en": "Dr. Sarah Farouk",
          "name_ar": "د. سارة فاروق",
          "specialty": { "id": 1, "name_en": "Cardiology", "name_ar": "أمراض القلب" }
        },
        "date": "2026-10-15",
        "start_time": "14:00",
        "end_time": "14:30",
        "status": "scheduled",
        "visit_reason": "Follow-up consultation",
        "can_change": true
      }
    ]
  }
  ```
  `can_change` = status is `scheduled`, the appointment is in the future, and the 4-hour change window is still open (computed by the backend, so the agent never calculates time rules itself).

### 6.3. `GET /patients/me/appointments/{appointment_id}`

- **Response `200`:** one appointment object as in §6.2, plus `created_at`, `updated_at`, and when cancelled `cancelled_at`, `cancellation_reason`.
- **Errors:** `404 APPOINTMENT_NOT_FOUND` (also when owned by someone else).

---

### 6.4. `POST /patients/me/appointments` — book

- **Headers:** `Idempotency-Key` (required)
- **Request:**
  ```json
  {
    "doctor_id": 12,
    "date": "2026-10-15",
    "start_time": "14:00",
    "visit_reason": "Follow-up consultation"
  }
  ```
  `visit_reason`: optional, ≤ 300 chars, administrative only.
- **Rules:** all of ADR-003 §3.5 (grid, shift, closures, time off, lead time, horizon, daily and active limits, no conflict), checked in one transaction (database-schema §5).
- **Response `201`:** the appointment object (§6.2) with `created_at`.
- **Errors:** `404 DOCTOR_NOT_FOUND`, `409 SLOT_UNAVAILABLE`, `409 DAILY_LIMIT_REACHED`, `409 DUPLICATE_DOCTOR_SAME_DAY`, `409 ACTIVE_LIMIT_REACHED`, `422 INVALID_SLOT_TIME`, `422 CLINIC_CLOSED`, `422 DOCTOR_UNAVAILABLE`, `422 BOOKING_TOO_SOON`, `422 BOOKING_TOO_FAR_AHEAD`, idempotency errors.

### 6.5. `POST /patients/me/appointments/{appointment_id}/reschedule`

Moves the appointment to another slot **with the same doctor**.

- **Headers:** `Idempotency-Key` (required)
- **Request:**
  ```json
  { "date": "2026-10-17", "start_time": "15:00" }
  ```
- **Rules:** the **current** appointment must be `scheduled` and ≥ 4 hours away; the **new** slot must satisfy all booking rules (the moved appointment is excluded from both daily and total active counts). All-or-nothing: on any error the original appointment is unchanged.
- **Response `200`:**
  ```json
  {
    "id": 501,
    "doctor": { "id": 12, "name_en": "Dr. Sarah Farouk", "name_ar": "د. سارة فاروق" },
    "date": "2026-10-17",
    "start_time": "15:00",
    "end_time": "15:30",
    "status": "scheduled",
    "previous": { "date": "2026-10-15", "start_time": "14:00" },
    "updated_at": "2026-10-10T20:05:00Z"
  }
  ```
  The status stays `scheduled`; the change is recorded in `appointment_history` as `time_changed`.
- **Errors:** `404 APPOINTMENT_NOT_FOUND`, `409 APPOINTMENT_NOT_ACTIVE`, `422 CHANGE_WINDOW_CLOSED`, `422 SAME_SLOT`, plus every booking error from §6.4.

---

### 6.6. `POST /patients/me/appointments/{appointment_id}/cancel`

- **Headers:** `Idempotency-Key` (required)
- **Request:**
  ```json
  { "reason": "Schedule conflict" }
  ```
  `reason`: optional, ≤ 300 chars.
- **Rules:** appointment must be `scheduled` and ≥ 4 hours away. Sets `status = cancelled`, frees the slot, writes history.
- **Response `200`:**
  ```json
  { "id": 501, "status": "cancelled", "cancelled_at": "2026-10-10T20:10:00Z" }
  ```
- **Errors:** `404 APPOINTMENT_NOT_FOUND`, `409 APPOINTMENT_NOT_ACTIVE`, `422 CHANGE_WINDOW_CLOSED`, idempotency errors.

### 6.7. `POST /patients/me/tickets`

- **Headers:** `Idempotency-Key` (required)
- **Request:**
  ```json
  {
    "subject": "Billing inquiry about lab test",
    "description": "Caller asked about the invoice for last week's blood test.",
    "priority": "normal"
  }
  ```
  `subject` ≤ 255 chars; `description` ≤ 2000 chars; `priority`: `low` | `normal` | `high` (`urgent` → `403 ACTION_NOT_ALLOWED`).
- **Response `201`:**
  ```json
  { "id": 801, "subject": "Billing inquiry about lab test", "status": "open", "priority": "normal", "created_at": "2026-10-10T20:15:00Z" }
  ```

## 10. Implementation invariants clarified during review

- **Idempotency fingerprint:** SHA-256 of canonical JSON containing operation, normalized route target (including appointment id for cancel/reschedule) and validated body with defaults applied. The same key on appointment A and B is a different fingerprint even with identical bodies. Authentication/session validation runs before every replay. Reserve the key, mutate clinic data, append history and persist the successful response in one transaction. Use a savepoint for domain failures if storing their terminal responses. A crash cannot leave a committed mutation without its replay response; an uncommitted reservation rolls back. `IDEMPOTENCY_IN_PROGRESS` describes lock contention, not a permanently abandoned row.
- **Identity concurrency:** serialize verification/session replacement per conversation before locking its challenge. After resolving a code, invalidate every other pending challenge in that conversation, including the other purpose, so a stale form cannot unexpectedly switch accounts. Logout and explicit call end also invalidate pending challenges. Polling `verified` reflects a currently valid binding; it does not refresh patient idle expiry. Expired sessions are revoked before inserting a replacement under the live-session unique index.
- **Challenge indistinguishability:** unknown and duplicate accounts receive the same pending state, expiry, attempt counters, errors, rate buckets and comparable verification work as known accounts. Perform a constant-time comparison against a dummy HMAC for unusable challenges. Send mail asynchronously through the adapter; account-dependent SMTP latency/errors must not leak existence through the request response. Operational delivery failures are reported without identifying whether a particular account exists.
- **Email normalization:** trim and lowercase the complete address for this synthetic clinic before lookup, registration, uniqueness checks and rate limiting. Validate `full_name` length 1–255 after trimming, `preferred_language` in `ar|en`, required fields and privacy consent. Ticket subject length is 3–255; description is 10–2000.
- **Time boundaries:** lead time ≥ exactly one hour; horizon ≤ exactly `now + 30 days` as elapsed time; change notice ≥ exactly four hours. Convert Cairo local slots to exact instants before comparison. Availability cannot enforce patient-specific limits because it is public; writes enforce them. Rescheduling excludes the moved appointment from both active and daily counts. Time-of-day filters are lower-inclusive and upper-exclusive.
- **Conversation lifecycle:** expiry is checked on each request, not only by cleanup. Gateway liveness detects dropped transports and reports disconnect; one active transport per conversation is allowed. Explicit End and text-session close are reported by the gateway using service credentials. Connection ownership prevents an old socket from ending a newly resumed call. Tokens travel over HTTPS/WSS and stay out of URLs, model context and logs.
- **Phase 2 escalation dependency:** queue creation, staff authentication and queue acceptance/read contracts must be specified together before implementation. A log or queued request is not a completed live transfer. Anonymous callers can request help without a patient session, but staff access never becomes public.


## Patient browser portal (opt-in, 2026-10-17)

Approved patient flow: email/password signup with email OTP, then email/password
or phone/password login, and email-link password recovery. This is separate from
service-token agent routes. Enable `PORTAL_ENABLED` to serve `/portal/auth.html`
and the following same-origin endpoints. See
[setup and acceptance](../development/patient-portal-auth.md).

All mutations require an exact `Origin` matching `PORTAL_ORIGIN`, JSON input,
and persisted rate limits. No service/admin token belongs in this frontend.
Success responses never contain passwords or provider tokens. Cookies are
HttpOnly, SameSite=Strict and Secure outside loopback development. GET session
returns only customer_number, first_name and preferred_language. Responses are
not cached. Input DTOs: `clinic_schemas.portal`.

| Method/path under `/api/v1/portal` | Input | Success |
| --- | --- | --- |
| POST `/signup` | Registration fields + password, password_confirm (12–128 characters) | 202 delivery=email; sends signup OTP |
| POST `/verify` | email, code, registration | 200 PatientProfile; binds verified Auth identity |
| POST `/resend` | email | 202 delivery=email |
| POST `/login` | identifier (email or canonical/Egyptian mobile), password | 200 PatientProfile |
| GET `/session` | HttpOnly cookies | 200 PatientProfile; refreshes provider token when necessary |
| POST `/logout` | empty object | 204; revokes provider/local binding and clears cookies |
| POST `/recover` | email | 202 generic response; reset link if account exists |
| POST `/recovery-session` | access_token from verified recovery callback fragment | 204; short-lived HttpOnly recovery cookie |
| POST `/reset-password` | same registered email, password, password_confirm | 204; changes Auth password, revokes sessions, clears cookies |

Email is unique case-insensitively; canonical phone is unique across patients.
Phone remains clinic profile data: phone login resolves the linked email privately,
then performs the normal Supabase password grant. No SMS verification is implied.
Duplicate errors are 409 `PHONE_ALREADY_REGISTERED` or `EMAIL_ALREADY_REGISTERED`.
Wrong credentials return generic 401; wrong origin returns 403; throttling 429.
A profile conflict after successful OTP may return `details.email_verified=true`;
retry with corrected profile data uses the already verified HttpOnly identity.
The browser cannot bypass verification by changing its view/hash.
